## 1. Testing philosophy and the determinism contract

### 1.1 What makes this system testable

The architecture is built on four properties that convert verification from "trust the code" into "compare a hash" (`03-…` §1–2, `04-…` §1.1):

| Property | Consequence for testing | Source |
|---|---|---|
| **Geometry is a pure function of a revision triple** `paginate(ms_rev, cmp_rev, dsg_rev, target)` | The pagination pipeline is called directly in a test with three literals; no server, no UI, no network | D-04, `03-…` §1 |
| **Revisions are content-addressed** (`sha256` over canonical JSON) | Two runs are equal iff their hashes are equal; "approved" is decidable, so a golden test is a hash comparison | D-10, `04-…` §1.1 |
| **Refusal instead of approximation** | "What does the system do when it cannot comply" is a first-class, assertable behaviour (it emits a `Finding` or refuses to render), not an error path | `04-…` §7.2, `07-…` §5.4, `17-…` §4.5 |
| **Measurement is one pinned Chromium, quantised to 1/64 px integers** | Font metrics and line breaks are reproducible across machines given the pinned build and font hashes | D-01, D-14, `07-…` §4.5 |

### 1.2 The core rule

> **A claim of determinism without a golden test is not a claim.** (`docs/00` §4.3, D-04)

Every behaviour this specification calls deterministic **must** have either (a) a golden test that hashes its output, or (b) a property test that asserts an invariant over generated inputs. A PR that adds a deterministic-looking function without one of these is incomplete by this plan's definition. The list of claimed-deterministic behaviours is `03-…` §2 (the determinism-boundary table); that table is the checklist, and §3 below has a row for each of its rows.

### 1.3 The anti-pattern this plan exists to prevent

**Data-level assertions passing while the rendered artifact is wrong.**

The failure mode: a `PagePlan` reports `sum(span lines) == measured lines` (`COMP_BLOCK_LOST` clear), `print.page_count % 4 == 0` (`PRINT_PAGE_COUNT_NOT_MULTIPLE_OF_FOUR` clear), every `text_hash` matches — and the produced PDF still clips a descender, drops a glyph the font lacks, or the spread view overlaps its gutter. Every one of those is a *rendering* fact that lives in pixels, and no assertion over the plan can see it.

Three laws follow, and every visual family in §3 obeys them:

1. **Assert the output, not the intention.** A test may not assert that a function "will" avoid clipping; it asserts that the rendered pixels did not clip (`DIG_TEXT_CLIPPED`/`PRINT_TEXT_CLIPPED`, `05-…` Part 3 inv 10).
2. **Every visual claim is tested against rendered pixels.** A `PagePlan` is an intermediate data structure. Structural claims (page count, span coverage, break positions) may be asserted against the plan, but each such claim is *independently re-derived from the render*: the HTML is measured by the same Chromium and the PDF is rasterised, and the two must agree (§6, §7). A plan-level green with no render-level counterpart is a gap, not a pass.
3. **Refusal is a testable outcome.** "The render was refused and nothing was emitted" is asserted explicitly (`07-…` §5.4 rule 2): a refused render must produce **no artifact at all**, never a partial one.

### 1.4 Determinism boundary as a test obligation

Every "Yes" row of `03-…` §2 has a golden or property test in §3; every "No" row (AI prose, ideation) is covered only by provider-stub and proposal-state tests (§5), because non-deterministic output cannot have a golden. The "Mixed" rows are split: the deterministic half is golden-tested, the AI half is tested for *schema and provenance*, never for content.

## 2. Test layers

Frameworks and directories follow `03-…` §4. Columns: **may assert** (what the layer is allowed to claim), **never used for** (the misuse the layer exists to prevent), **budget** (wall-clock on the reference host), **gate** (what a failure blocks).

| Layer | Framework | Directory | May assert | Must never be used for | Budget | Gate |
|---|---|---|---|---|---|---|
| **Unit** | Vitest | `tests/unit/` | pure-function behaviour: canonical JSON, hashing, solver costs, density math, span arithmetic, block/beat stability, migrations, provider cache keys | rendering, pixels, timing, browser behaviour | ≤ 60 s | commit |
| **Golden / snapshot** | Vitest + committed fixtures | `tests/golden/` | equality of a **hashed** plan / revision / finding-set against a committed golden; the hash **is** the assertion | re-baselining automatically; asserting a human-readable diff of prose | ≤ 90 s | commit |
| **Property-based** | fast-check | `tests/property/` | invariants over generated revision triples / lock sets / page counts (never output values) | finding the specific page a break lands on (that is golden) | ≤ 120 s | commit |
| **Visual regression** | Playwright + rasteriser | `tests/visual/` | rendered HTML screenshots at the viewport matrix; rasterised PDF pages; a diff ratio against a committed baseline | correctness of *meaning*; anything not derived from a render | ≤ 8 min full / ≤ 90 s subset | commit (subset) · nightly (full) |
| **Integration** | Playwright driving the studio UI | `tests/integration/` | end-to-end user operations: editor ops, job progress, approvals, exports — through the real Fastify server and real Chromium | unit-level logic (call the function directly); pixels (that is visual) | ≤ 5 min | commit · phase |
| **Acceptance** | Playwright + CLI (`sbx`) | `tests/acceptance/` | the `A-01`…`A-18` demonstrations (§14) on the reference fixture; all are end-to-end | inventing new acceptance criteria; A-18 is manual (§3.18) | ≤ 8 min | phase |
| **Performance / determinism** | Vitest + Node timers | `tests/acceptance/perf/` | named budgets (§9); identical-input hash/byte equality (§7) | micro-benchmarking a single function in isolation | ≤ 6 min | nightly · phase |

**Layer rules**

- A test lives in exactly one layer. If it needs a browser it is not a unit test; if it needs the UI it is not integration-free.
- `tests/unit/` may not import `playwright` or touch the filesystem outside a temp project directory.
- The visual and golden layers may not be auto-updated by CI (§6.4, §7.3). Updating a golden or baseline is a reviewed diff.
- No layer may call a live AI provider (§5). Provider access is stubbed in every gating layer.

## 3. The test catalogue

Columns: `T-<AREA>-<nnn> | name | layer | what it asserts | fixture | spec cite`. Fixtures are named in §4. `layer` uses the §2 names.

### 3.0 Table conventions — three row shapes, and which is which

The catalogue uses three column layouts. They are deliberate, and each table's header states its own; a reader (or a parser) must not assume one shape for the whole document.

| Where | Columns | Why this shape |
|---|---|---|
| §3.1 – §3.22 | `ID \| Name \| Layer \| Asserts \| Fixture \| Cite` | the standard shape: a test that exists because a behaviour needs testing |
| §3.16 (studio editor operations) and §7 (determinism) | `ID \| Operation/Name \| Layer \| Asserts \| Cite` | no Fixture column: the fixture is the running studio and the e2e harness itself, which is not a fixture artefact |
| §3.23 – §3.24 (requirement-completing tests) | `ID \| Verifies (R-) \| Name \| Layer \| Asserts \| Fixture \| Cite` | an extra leading column, because these tests exist *to complete a requirement* and the requirement they close is the primary fact about them |

**A definition row is any row whose first cell is the test id itself** (`T-<AREA>-<nnn>`). Rows whose first cell is an acceptance id (`A-nn`), a phase number or a fixture name are mapping/coverage rows: they *mention* tests without defining them. Both `tools/gen-checklist.py` (`C1`/`C2`/`C7`) and `tools/check-traceability.py` key on that distinction, which is why `C2` cannot be satisfied by an acceptance-mapping row.

### 3.23 Requirement-completing tests

The catalogue above (§3.1–§3.22) was authored with this plan's own test numbering, independently of `docs/01`'s requirement numbering. Every requirement in `spec/requirements.json` carries a `verification` id, and **that id is authoritative**: it is the identifier `docs/15-development-checklist.md` renders, and it is owned by this plan (`docs/00` §3.2). This subsection completes every requirement the catalogue above does not already complete, in one of two ways:

1. **A test whose id is the requirement's `verification` id.** Where `docs/01`'s requirement number did not collide with an id already declared in §3.1–§3.22, the requirement-completing test takes that id directly — the `VSN`, `PUB`, `WIZ`, `PRT` and `OPS 001–009` bands, `T-IDE-010`…`T-IDE-016`, `T-GEN-005`…`T-GEN-014`, `T-DIG-011`…`T-DIG-017`, `T-DSN-009`…`T-DSN-013`, `T-QAS-010`…`T-QAS-017`, `T-UXS-101`…`T-UXS-104`, `T-ARC-101`…`T-ARC-105`, and the `1xx` bands.
2. **A test with a new id, where the requirement number already named an unrelated test.** For 98 requirements the two numbering passes collided: the named id was already declared above for a *different* subject (`R-CMP-001` named `T-CMP-001`, declared above as `dp-optimality`; `R-IDE-001` named `T-IDE-001`, declared as `blueprint-gate`). Those 98 are now repointed at a test that genuinely covers them — either an existing test (its own definition row in §3.1–§3.22 carries the added `R-` back-reference) or a requirement-completing test declared here under an id that extends past its area's current maximum. The 38 new ids are declared in the subsections below and in §3.23.13.

Columns: `T-<AREA>-<nnn> | verifies (R-<AREA>-<nnn>) | name | layer | asserts | fixture | cite`. The **verifies** column is the `R-` back-reference that §10.1 requires of every row. `layer` uses the §2 layer names; `manual` marks a human-reviewed test (§11). The six budget rows are declared at the `acceptance` layer because §2 places performance and determinism under `tests/acceptance/perf/` (§9).

**Numbering.** An id is used here only if it is not already declared anywhere in this plan; the frozen ids cited by `docs/08`, `docs/10`, `docs/13`, `docs/15` and `docs/16` are never reused, renumbered or deleted. Where a requirement's id sits below its area's current maximum (IDE, DIG) the free number is used directly; elsewhere — including every new id added by the repointing above — the numbering extends past the area's current maximum (`T-IDE-102`+, `T-GEN-015`+, `T-CMP-096`+, `T-DIG-104`+, `T-DSN-103`+, `T-QAS-018`+, `T-UXS-105`+, `T-ARC-106`+, `T-OPS-105`+).

**Round-2 additions (same rule).** The tests declared for the second external review's findings — the derived-budget and page-count rows (`T-WIZ-015`, `T-WIZ-016`), the resolved-density-band row (`T-PUB-011`), the PDF-metadata and imposition-parity rows (`T-PRT-103`…`T-PRT-106`), and the waiver/`effective_blocking` gate rows (`T-OPS-107`…`T-OPS-109`) — extend their own areas the same way, past each area's current maximum. None renumbers, removes or repurposes an existing id, and each carries the `R-` back-reference of every requirement whose obligation it supports (§10.1); where a row is a **second verifier** of a requirement whose `verification` id stays elsewhere (`T-PUB-011` on `R-PUB-010`, `T-PRT-103` on `R-PRT-001`, `T-PRT-104`/`T-PRT-105` on `R-PRT-012`, `T-OPS-107`/`T-OPS-108` on `R-OPS-102`, `T-OPS-109` on `R-IDE-015`) it is an addition, not a replacement, exactly as §3.24's `T-OPS-052` is.

**Round-3 addition (same rule).** One test is added for the length model's measured input: **`T-WIZ-017`** (`measured-words-per-line-pinned-to-probe`, §3.23.3) pins `words_per_line_measured` to the version-controlled probe `fixtures/measure/probe.en.early.txt`, so a change to the probe's contents — or to the `dsg_rev` it is measured on — without re-deriving the budget fails loudly. It extends `T-WIZ-015`/`T-WIZ-016` and, like them, cites `R-WIZ-015` without changing that requirement's `verification` id (a requirement may have several verifying tests, §10.1). It is declared because the constant it guards had rested, unnoticed through three review rounds, on a probe file that had never been created (`05-…` §1.6 item 6).

**Round-4 additions (same rule).** Two things are added for the fourth correction of the same constant. **`T-WIZ-017`** gains the **rendered-face assertion**: a measurement must assert the face it rendered in by comparing advance widths against a family that cannot exist, because `document.fonts.check()` reports an unavailable family as available and `document.fonts.load()` given a whole quoted stack resolves without loading anything; the bridge and the emitter must read the same `app/assets/fonts` directory (`08-…` §2.6.1). And **`T-WIZ-018`** (`line-budget-split-and-prose-budget`, §3.23.3) declares the new rule `R-WIZ-017`: the story pages are not all prose, so the budget must be derived from `lines_available_for_prose` (the `144` total less the `26` scripture lines and the `1` heading line = `117`), never from the total — `117 × 7.9 = 924 _words_`, not the `1106` the total-line formula yields (`05-…` §1.6 item 7). Like the round-3 addition it extends its area past its current maximum and changes no existing id.

### 4.3 How fixtures are pinned so a change is visible in review

- Every fixture directory carries a committed `FIXTURE.lock.json`: the canonical-json `sha256` of each revision and of the fixture tree. A test asserts the lock matches the tree (`T-ARC-…`, added with the fixture).
- Golden plan hashes and PDF byte-hashes are derived from fixtures and committed. A fixture edit therefore changes **both** `FIXTURE.lock.json` and the dependent goldens — two visible, reviewable diffs, never a silent drift.
- Fonts, the scripture registry and the Chromium build are pinned by hash (D-09, D-14); a fixture cannot silently depend on an unpinned font or translation.
- No fixture change may be accepted to make a test pass; it must be justified as a change of the *fixture*, reviewed as such (§7.3).

### 4.4 Rule: no test may depend on a live AI provider

Every layer except the opt-in live-smoke set (§5) resolves the provider interface to the deterministic stub (§5). A gating test that reaches a network provider is a defect: the provider module is replaced at the module boundary, and a test asserts the real transport is unreachable during gating runs (`T-ARC-028` pattern, extended to the content engine).

## 5. Provider stubbing

### 5.1 Deterministic stub, keyed by prompt hash

The `Provider` interface (`03-…` §7) is satisfied in tests by a stub that reads **recorded response fixtures** keyed by `prompt_hash`:

```
fixtures/providers/<prompt_hash>.json
  { "prompt_hash": "...", "request_kind": "ideate|draft|review|restructure|pageturn|rewrite|scripture_review",
    "input_hash": "...", "provider": "stub", "model": "stub-1", "response": { ... }, "tokens": {"in":0,"out":0} }
```

Rules:

1. **Unknown prompt hash fails loudly.** If a test asks for a task whose `prompt_hash` has no recording, the stub throws — so a prompt-template edit (which changes the hash) is caught rather than silently serving stale content.
2. **The stub is byte-deterministic**: the same request returns the same bytes every run, which is what makes the provider cache test (`T-ARC-021`) and resume test (`T-ARC-023`) meaningful.
3. **Recordings are committed fixtures.** Re-recording is a reviewed diff against a *live* run performed outside CI (§5.2).
4. **Schema-rejection and failure modes are curated fixtures** (`prov-bad-schema`, `prov-flaky`, `prov-interrupted`), not random.

### 5.2 Live provider smoke tests — opt-in, never gating

A separate suite (`tests/live/`, excluded from every gating layer) exercises real providers:

| Property | Rule |
|---|---|
| Selection | runs only when explicitly invoked and a provider credential is present in the environment |
| Gate | **never** in the commit, nightly-gating or phase-gate path; a failure is advisory |
| Purpose | detect provider API drift and validate that a freshly recorded fixture still matches reality |
| Output | may propose a re-recorded fixture, which is then reviewed as a normal fixture diff |
| Absence | if no credential is present the suite is skipped, not failed |

A CI policy test asserts that no `tests/live/**` path is referenced by the gating configuration (§8).

## 6. Visual regression mechanics

### 6.1 Viewport matrix and DPR

| Parameter | Value | Source |
|---|---|---|
| Viewports | 360×640, 414×896, 768×1024, 1280×800, 1440×900 | `03-…` §5.1 |
| Spread enabled | ≥ 1024×768 | §7.1, `03-…` §5.1 |
| Device scale factor (DPR) | **1** for all measurement and screenshots (reproducibility over fidelity) | D-01, D-04 |
| Orientation | portrait (default) + landscape (swap) for each viewport | §7.1 |
| PDF rasterisation | 150 DPI, one PNG per page | §9.3 |

### 6.2 Font loading and render settling

Before any capture or measurement the harness:

1. waits for `document.fonts.ready`, and for each used `(family, weight)`, `document.fonts.load(...)`;
2. polls layout until two consecutive measurements are identical (the font-settling race, `T-DIG-003`);
3. disables animations (`prefers-reduced-motion: reduce`, CSS `animation:none`), hides the caret and scrollbars, and fixes the viewport exactly.

### 6.3 What counts as a difference

| Kind | Rule |
|---|---|
| Pixel diff | per-page anti-aliased diff (pixelmatch-style, per-channel threshold `0.1`) |
| Allowed | diff ratio ≤ 0.1 % of pixels **and** no single differing cluster larger than 8×8 px |
| Failing | any diff over the allowance, or any cluster over the size cap |
| Structural (PDF) | MediaBox dimensions, page count and font embedding are asserted **structurally**, not by pixels (`T-PRT-060`…063) |
| Clipping | a dedicated crop check asserts no text reaches or crosses the content-box boundary (`T-CMP-039`) |

### 6.4 Accepting a legitimate change

- Baselines are committed under `tests/visual/__baseline__/`.
- A legitimate change is accepted only by regenerating the baseline (`UPDATE_SNAPSHOTS=1`) **locally** and committing the new baseline **with a rationale in the PR**. CI never writes a baseline, and a diff in CI is a failure, not an update.
- A baseline change and a fixture change are reviewed together: the `FIXTURE.lock.json` diff (§4.3) shows whether the input changed or only the renderer did.

### 6.5 Where diffs are stored

`tests/visual/__diff__/<suite>/<test>/` holds `expected.png`, `actual.png`, `diff.png`. This directory is **gitignored** and uploaded as CI artifacts on failure; it is never committed.

### 6.6 How PDF pages are rasterised for comparison

1. The print renderer produces the reading PDF (`T-PRT-060`) via Chromium `page.pdf({preferCSSPageSize:true})` (`03-…` §5.3).
2. The harness rasterises each PDF page with `pdftoppm -r 150 -png` (or an equivalent fixed-resolution rasteriser) into one PNG per page.
3. Each PNG is compared to the committed baseline for that page number using the allowance of §6.3.
4. The HTML storybook is screenshotted directly at the viewport matrix (not via PDF) so the digital and print paths are visually tested independently.

| ID | Name | Layer | Asserts | Cite |
|---|---|---|---|---|

## 8. CI

### 8.1 What runs, and when

| Stage | Suites | Budget | Gate |
|---|---|---|---|
| **Every commit** | unit, property, golden, visual **subset** (reference viewports 360×640 + 1280×800 only), integration (smoke) | ≤ 6 min | blocks merge on red |
| **Nightly** | full visual matrix, full integration, performance budgets, determinism, migration matrix, acceptance (A-01…A-17) | ≤ 35 min | blocks the nightly badge; red is reported |
| **Phase gate** | the current phase's required tests (spec §17) + all layers green | ≤ 45 min | **a red test blocks phase exit** |
| **Opt-in live** | `tests/live/**` | unbounded | **never gates** (§5.2) |

Phase-to-suite mapping is the test-layer view of `docs/13` §2–§3 (authoritative for phase content, the 1A/1B/1C split of Phase 1, and the 4a–4d split of Phase 4). It follows the nine phases of spec §17:

| Phase (§17) | Gate requires (additional) |
|---|---|
| 1 Content Foundation | `T-ARC-0*`, `T-IDE-0*`, `T-GEN-0*`, `T-WIZ-0*` |
| 2 Structured Composition | `T-CMP-0*` (solver, invariants) |
| 3 Interactive HTML Reader | `T-DIG-0*` (pagination, reader) |
| 4 Page Composition Editor | `T-UXS-0*` |
| 5 Shared Design System | `T-DSN-0*` |
| 6 Print Renderer | `T-PRT-02*…06*` (print, PDF), `T-PRT-103`, `T-PRT-106` |
| 7 Booklet Publishing | `T-PRT-04*` (imposition), `T-PRT-070`, `T-PRT-104`, `T-PRT-105` |
| 8 Automated QA | `T-QAS-0*`, `T-CMP-03*` |
| 9 End-to-End Validation | `A-01`…`A-18` (A-18 manual) |

### 8.2 Pinned Chromium provisioning

- Playwright's bundled Chromium is pinned to an exact version in the lockfile; CI installs it with `npx playwright install --with-deps chromium` and caches `PLAYWRIGHT_BROWSERS_PATH`.
- A startup assertion (`T-OPS-033`) checks the installed build id equals the pinned id and refuses to run otherwise — a green suite on the wrong browser would be a false pass (D-01, D-14).

### 8.3 Caching

| Cached | Key | Note |
|---|---|---|
| Playwright browsers | pinned version | provisioned, not rebuilt |
| package-manager store | lockfile hash | — |
| measurement results | `(revision triple, viewport)` | `project/.cache/measure/`; disposable (`T-OPS-035`) |
| provider recordings | committed fixtures | not a runtime cache; no re-spend needed |

Golden and visual suites are the slow layers by design; measurement caching keeps the golden suite under ~90 s and the visual full matrix under ~8 min (§2).

### 8.4 The gate rule

**A red test blocks a phase exit.** A phase is complete only when its required suites are green on the pinned environment. Skipped tests count as red unless the skip is the A-18 manual sign-off (§11) or the opt-in live suite (§5.2).

## 10. Coverage and traceability

### 10.1 The mechanism (not the dump)

- Every test row in §3 carries a `spec cite` and, where it exists, an `R-<AREA>-<nnn>` (`docs/00` §3.1). `docs/15-development-checklist.md` renders the full `R-` ↔ `T-` matrix from these citations; this plan does not duplicate that table.
- Rule: **every requirement `R-<AREA>-<nnn>` must be covered by ≥ 1 `T-<AREA>-<nnn>`, or explicitly marked manual / not-machine-testable with a reason.** An uncovered, unmarked requirement is a defect in `docs/15`.
- The mapping is enforced **bidirectionally**. Forward: every requirement names a `verification` id this plan declares (`tools/gen-checklist.py` check `C1`). Backward: the row that *declares* that id — a **definition row**, whose first cell is the `T-` id itself, not an acceptance-mapping row (`| A-01 | … | T-IDE-001, T-IDE-002 |`) or a phase-coverage row that merely mentions it — must carry that requirement's `R-` id (`check C2`). A `C1`-clean set can still fail `C2`: the id is declared, but the test it declares is about a different subject. Both checks must report zero.
- The mapping is also checked mechanically by enumeration: a test walks every `R-` in `docs/01` and asserts each appears in the coverage map, or in the explicit manual list (§11).
- The reverse of `C1` — a `T-` id **cited by any document in `docs/`** that this plan does not declare — is enforced too, as `tools/gen-checklist.py` check `C7`: an id a document cites must have a definition row here, or the citing document names a test that does not exist. `C7` reports each offending id with the files that cite it and exits non-zero while any remain, so the class found in `docs/12` §6 and `docs/16` §6 cannot recur silently (see §12 note 7; the tests are declared in §3.24).

### 10.2 Minimum coverage rule per module

| Module (`03-…` §4) | Minimum | Rationale |
|---|---|---|
| `core` (ids, hashing, canonical json, units) | 100 % branch | a bug here invalidates every hash-based claim |
| `composition/solver` | 100 % branch on cost/edge/tie-break paths | the load-bearing deterministic core |
| `composition/density`, `composition/pagerun` | ≥ 95 % branch | boundary-heavy |
| `digital/measure` | ≥ 90 % branch **plus** a golden on every fixture | the browser boundary is not fully branchable |
| `print/imposition` | 100 % of `M∈{8,12,16}` tables + the permutation property | arithmetic must be exhaustive |
| `validation` | 100 % of registered codes have a trigger + a negative fixture (§3.12) | the registry is the QA contract |
| `project` (revisions, approvals, migrations) | 100 % branch | approval/refusal correctness |
| `providers`, `jobs` | ≥ 90 % branch | failure modes are curated fixtures |
| `studio` (UI) | every §6.4 operation has an integration test (§3.16) | coverage-by-operation, not by line |

Coverage is enforced by Vitest thresholds per directory; a drop below the floor fails the commit gate.
